## 已修改

- `dispatch` 描述明确新任务、继续、追加和改约束都需要交接；`cancel` 不得只口头答应，并排除“先别停”。
- 收窄“host 事实播报不调用工具”的适用范围，使其不覆盖新的用户动作。消除调用前口头接单与 cascaded 单响应契约冲突，区分新追加要求与重复派单。
- 确认明确同意/拒绝/取消才提交；尚未决定和追问不自动当拒绝。实际授权与状态校验仍归宿主，未新增关键词路由或强制 tool_choice。
- 明确禁用能力。联网搜索请求可查询记忆，但续答须说明回忆结果和搜索不可用；普通记忆查询不受这条规则影响。禁用 coding 直接说明，停止征集需求。
- 明确记忆 `scope` 是 recent/any 的时间范围，`source` 才是 session/personal 的来源；一般讨论无需查历史。
- 评分器支持可选回忆分支 `otherwise`，以及多组答案证据 `textAll`；直接解释限制与回忆后解释均可通过。
- 加入取消否定、只讨论、确认追问三个反例。保留原始用户输入，不通过改写成显式工具指令降低难度。

## Max 暴露的真实适配器 bug

`qwen3.8-max` API 接受模型名，原始响应也报告这个模型。普通对话可通过，但工具流在已建立 call ID 后出现 `id:null` 的后续参数增量，原适配器将其当作非法 ID 丢弃整个调用。此前 Flash 暴露的是 `arguments:null`，属于另一个字段。

修复只令空增量不覆盖已收集的值；缺少最终 ID、改变 ID、空参数或非法 JSON 仍拒绝。捕获响应回放先失败、修复后成功，并验证 missing/changed ID 不可产生调用。`tool-null-id-delta.json` 去掉了与传输校验无关的 reasoning_content；抓包报告也不含密钥。

中止的 `qwen-max-before-null-id-interrupted.json` 仅保留排障证据，不计入能力比较。它没有 finishedAt，不能当作完成的验收批次。

## 剩余失败逐项

Flash：`coding-disabled` 一次明确说不可用后，仍补充“如果您有具体的修改需求……请告诉我”。按用户确定的规则，这仍然失败；没有放宽它。

Max 等义表达修正后仍有四项：

1. `confirm-ambiguous`：用户尚未决定，模型调用 memory 查询当前进度；没有错误同意/拒绝，但发生了不必要的工具调用。
2. `confirm-question`：询问为何建项目时转查历史原因。零调用断言因此失败；查询历史是否属于合理解释路径需要产品规则进一步明确，不能一概归为模型无能力。
3. `search`：把“今天”变成没有依据的 `2026年7月21日`。该 fixture 没有提供当前日期，属于真实参数依据问题。
4. `knowledge-failure`：拿到失败结果后又检索一次。违反当前一轮失败说明的验收约定，但是否允许有界重试是工具恢复策略问题；没有把它伪装成已通过。

四个已修正的评分假阴性：两次“不要修改业务逻辑 / 不得改动任何业务逻辑”保留了约束；摄像头“没法用”和知识库“用不了”明确表达不可用。新增等义断言回归先失败再通过，仍拒绝删除业务约束和虚构执行。

## 模型选择

用户决定继续使用 Flash。生产 Qwen cascaded 默认模型仍为 `qwen-flash`，本轮未修改用户配置；主验收使用 Flash，Max 保留为诊断对照。

## 对模型归因的结论

Max 用旧提示也能完成四个动作场景，说明 Flash 的第一组问题与完整提示下的遵循稳定性有关；不能都算作宿主生命周期 bug。另一方面，Max 原始工具响应被宿主 parser 丢弃，已确定是代码兼容 bug。强模型也会多查工具、编造时间或走不同恢复路径，换模型不能排除提示和测试契约的影响。
