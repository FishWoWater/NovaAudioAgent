## 根因证据

当前系统提示有“小游戏未指定平台先问网页还是桌面”，但每轮提示又说“多种实现都符合请求不算需求缺失，交给执行器决定”；工具描述也只笼统要求“影响交付的缺项才先澄清”。失败调用原文直接出现“具体技术形式（网页或桌面等）未指定，可由执行器合理决定”。这支持提示词边界冲突的解释，不能只归因于模型鲁棒性。

V2 将未指定新产物交付形态作为先澄清条件，在三个提示面统一表达，删除了旧的宽泛实现选择表述。不增加关键词分类、强制工具调用或代码兜底。

## 未参与修改的反例：自动通过不等于体验通过

另加 6 个场景各 3 次：澄清后授权自行决定、回答未解决当前缺项、用户历史已明确形态、模糊优化、明确运行命令、未定义删除边界。工具契约自动判分 **18/18**，但人工审阅发现：

- 对“把这个项目优化一下”，三次回答仍围绕交付形式，其中两次明显把现有项目修改引向网页等新产物形式。
- 对“把这个系统里的过期记录都删掉”，一次问“清理脚本还是网页/桌面工具”，没有问删除范围和过期标准；另两次问到了范围及标准，但一次同时问了两个问题。
- 普通知识讨论、确认原因说明仍可能长篇输出；个别原因说明加入了没有证据的先前用户意图。

因此 **不把 V2 直接替换到正式提示词**。它证明统一边界能改善提前派发，也暴露了过度强调平台会让模型问错问题。下一步应区分当前动作：新建产物澄清使用方式，修改澄清目标，删除澄清范围与判定标准；这些是提示词中的语义职责，不是代码中的关键词路由。不要靠添加越来越长的例外列表修补。

## V3：结果歧义原则与评测口径修正

用户随后明确指出：没有必要每次问平台。因此旧套件中“平台未给出就必须追问”的通过条件不再作为产品要求；旧结果保留，不能与新口径混算。平台缺失本身不是需求未澄清的证据。

V3 只保留一套语义原则：不同的合理理解是否会造成明显不同的结果、使用方式或操作范围；结合已有上下文和明确委托判断。系统提示定义完整原则，每轮提示和 dispatch 描述引用它。不固定检查某个字段、不引入代码分类或重试兜底。候选存在私有实验文件，尚未进入正式提示词。

新口径的独立对照使用 16 场景 × 3 次，两组均为 `deepseek-flash`，关闭思考。同一场景的基线和候选并发，请求不执行返回的工具。保留明确执行、确认、取消、已有产物修改、纯工作区操作、命令执行；增加明确未决的删除边界，以及同样边界已经明确时应直接派发的对照。低风险小游戏和倒计时不强制问平台，允许直接派发；如果模型选择询问，单独人工审查其必要性，不能仅凭“说了话”认为交互优秀。模糊优化必须问清目标或只做不改变现状的发现，不能自行扩大为一揽子代码修改。删除范围未定必须先澄清。

原口径结果：`deepseek-v3-ab.json`。修正口径后的独立结果：`deepseek-v3-outcome-ab.json`。每个变体保存实际系统提示、工具描述、每轮提示及哈希；历史 `surfaceHash` 不是候选标识，应读取 `actualSurfaceHash`。该口径变化是用户明确修正产品要求，发生在新批次开始前，并非事后删掉失败样本。

### V3 新口径对照结果

完成 96 个场景运行（基线/候选各 48，16 场景 × 3 次）。基线工具契约通过 **44/48**，V3 **48/48**，本批不需要同义表达人工加分。基线失败为三次模糊优化直接扩大为代码修改，一次删除范围未定就授权执行器自行确认规则并删除。候选在这两类场景均先询问目标或范围；明确范围的删除、明确命令、修改已有产物、工作区操作、确认及取消未观察到新的工具契约失败。

但不能称为完整交互验收通过：

- 低风险游戏/倒计时共六次，V3 五次直接派发，一次仍同时追问平台和倒计时形式，属于不必要或过多澄清。此例虽按宽松工具契约通过，人工交互审阅不通过。
- 删除范围未定的三次，问题都相关，但均一次问了多个维度；其中一次额外问备份/预览，仍有减少认知负担的空间。
- 原口径的另一批 V3 还出现一次模糊优化直接派发。该场景要求没有随平台政策改变，说明即使新批次 3/3 正确，也不能宣称稳定零回归。两批原始记录均保留。

结论：这条原则比固定问平台更接近产品目标，且不需要新增关键词兜底；本轮只能证明有改善迹象，不足以自动替换正式提示词。实验候选与实际客户端仍隔离。没有将前台 API 通过等同于 coordinator、审批转发、真实语音或 Codex 执行验收。
