# DeepSeek Flash 派发依据复核

本次只审阅已保存的 `deepseek-v3-outcome-ab.json` 中 48 个候选场景运行，不改提示词、不新增模型重试、不执行返回的工具。旧的 48/48 是脚本对调用结构和预期动作的判分，**撤回将其解释为需求理解或产品验收通过的结论**。

## 固定审阅方法

逐例同时读取用户原话、宿主提供的相关上下文、多轮答案和最终工具参数，分别记录：

1. 决策依据：是否能指出可执行目标、相关上下文或明确委托；不能仅凭产物名称、通用工作区名称或“任务简单”推定需求充分。
2. 参数忠实度：目标、约束、范围是否被保留，有无擅自收紧或扩大；派发有依据不代表参数必然正确。
3. 澄清相关性：是否询问会影响当前任务的真实缺项；不以是否出现“平台”、问号数量或固定句式判断。
4. 授权及事实：未决状态不得变成批准、拒绝或取消；不能虚构先前请求和执行进展。

证据不足单列，不硬算成通过，也不简单断言模型一定理解错误。某个场景允许多种合理行为，但必须能解释行为与已有事实的关系。该审阅不是一份新的总体成功率。

48 个场景运行中发生 29 次 dispatch：26 次在首轮，3 次在明确暂停后经多轮补齐条件再派发。

- 尚未决定但询问原因 3 次：没有误调用；口播事实性另见下文。

- 倒计时 1 次：询问运行形式与固定时长/目标日期，两者与该任务相关，不再标记为“问平台所以失败”。

## 旧判分遗漏的具体问题

- `holdout-clear-delivery / repeat 0`：用户说“不用安装依赖”，参数却增加“不使用 npm、构建工具或外部库”。无需安装不等于禁止一切外部库；此例派发决策有依据，但参数忠实度存在问题。
- `confirm-question / repeat 1`：输入只给出“新建 demo 项目待确认”，回复说它是“为之前那个请求准备的”。触发请求并未提供，属于补写前情。没有误确认不等于口播事实正确。
- `holdout-workspace-only` 三例写了“新建与切换”：核对 `runtime/src/projects/project-store.ts` 的 `createManaged`，创建会设置 `activeWorkspaceId`，因此与当前创建行为一致，**不据此判为越界操作**。仍应区分用户原话和系统默认行为。
