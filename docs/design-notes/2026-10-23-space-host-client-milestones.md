# Space / Host / Client 里程碑与验收

日期：2026-10-23  
基线：`v1.0.0dev`，`ecb533f9`  
状态：草案，经过一轮 codex 评审的修订，未经产品负责人逐项确认。决策编号见[入口文档](2026-10-23-space-host-client-handoff.md)。

## 0. 总则

- 里程碑是**可独立验收**的阶段，不是工期承诺；本文不给人天估算（没有依据）。
- 每个里程碑以**证据**退出：构建 SHA、日志、截图或录屏、任务 / 消息 ID。仅凭界面显示“在线”或“已发送”不能证明没有重复执行或丢失（起点文档 §8 的要求，沿用）。
- 真机项（M0、M5、M6）需要实际设备、账号与证书，没有真机证据就**不能**写成“已验证”。
- 公开 / 内部边界与构建隔离见入口文档 §7。

## 2. M0 风险 spike

**目的**：把最大的未验证假设变成事实，再决定后面的设计是否成立。

**前置（需要产品负责人或公司提供）**

- Apple 开发者账号与能创建 APNs 密钥、App Group 的 provisioning。
- Firebase 项目与 `google-services.json` / FCM 凭证。
- 小米开放平台开发者账号、应用注册、推送凭证。
- 至少：一台 iPhone、一台带 GMS 的 Android、一台小米设备（HyperOS）。设备型号与系统版本要记录。

**范围**

| # | 验证项 | 退出证据 |
|---|---|---|
| S1 | iOS：APNs + Notification Service Extension 在锁屏下解密并改写通知；解密失败降级通用文案；NSE 能读到密钥（App Group / Keychain Access Group） | 真机锁屏录屏；降级用例录屏；记录 iOS 版本与是否在被杀进程下 |
| S2 | Android FCM data 消息 → `onMessageReceived` → 解密 → 本地通知。分别测：前台、后台、锁屏、被系统杀、用户 force-stop、Doze | 各状态下是否到达的表格，含设备与系统版本 |
| S3 | 小米：通知栏消息的通用文案；**透传消息**能否唤醒被杀进程并在锁屏下发本地通知；公信配额行为；包名与签名要求；海外与国内服务器差异 | 同 S2 的表格；向小米确认助手类消息归类（O6）的记录 |
| S4 | WebSocket 流式原型：首字延迟、断线重连、背压 | 延迟数据；中途杀 App 的行为记录 |

**产出**：一份 spike 报告，写明每个平台的“可行 / 不可行 / 有条件可行”与到达率的真实证据；据此修订架构文档 §10.4。

**风险**：S1 的 NSE 解密与 APNs 配置是整个方案**最大的未验证假设**。如果失败，要回到产品负责人，D17、D20 可能要重议。

## 3. M1 relay + 配对

**范围**：密文信箱、序号与游标、ACK、deadline、在线状态、实时流通道、签名校验、配额与准入的最小实现、扫码配对与密钥交换、设备撤销与密钥轮换、Docker 自托管。

**不含**：展示契约、Host 逻辑、推送接入（M6）。

**退出证据**

- 直接读 relay 存储只见密文与元数据（给出读取记录）。
- 撤销后，旧设备无法收发，重放旧消息被拒。
- 两个 Client 各自游标正确，互不影响。
- 去重：同一 `id` 重复投递只落一条。
- 背压：超限连接被断开并可重连补拉。
- 二维码一次性且会过期。
- **E2E 设计通过密码学评审**（O7），评审记录附在 PR 中。

## 4. M2 Host 并入 Hub

**范围**：Hub 的 Life / context / routing 逻辑并入桌面 Host；Host 主动连出 relay；删除 TS 侧 authority、schedule handoff、owner-revision。

**前置**：V1（确认 Hub 的 Life 副本与 `PersonalStore` 的关系，并入后只保留一份权威数据）。

**退出证据**

- Host 重启后游标续传，不丢不重。
- 全仓没有 `authority` 路由与 `space-authority` 引用（保留 `device/authority.dart` 的任务授权）。
- 既有 runtime 测试通过；被删模块的测试一并删除，且删除理由写进 PR。

## 5. M3 展示契约 + 创建 Space

**范围**：版本化视图（timeline、profile about、待办、目标、feed、通知、聊天消息）、协议版本握手、未知类型降级；“创建 Space”二选一（独立 / Client）与多 Space 的本地隔离（O9）。

**前置**：O4 的字段清单与最低版本协商方案先写成 schema 与文档，经评审再实现。

**退出证据**

- 旧 Client + 新 Host 的版本错位测试：Host 不发送无法降级的类型；未知卡片显示通用文本。
- Timeline 的忽略状态与实体 `version` 在投影里可表达。
- 创建 Space 后，两种模式的数据互相隔离。

## 6. M4 Client 意图

**范围**：完成待办、忽略卡片、创建与编辑目标和待办、编辑 profile about、手机采集输入；意图 ID 幂等；Host 落盘后回投影；取代 `life-sync.ts`。

**必须覆盖的语义**（架构文档 §8.2）：持久化 pending、ID 重映射与依赖顺序、版本冲突反馈。

**退出证据**

- 重复提交同一意图不产生重复变更。
- 提交后断网并重启 App，沿用原 `op_id`，Host 不重复创建。
- 先建目标再建关联待办，断线重连后顺序正确、引用被重映射。
- 双 Client 同时编辑 about，产生明确冲突，不静默覆盖。
- Host 离线时：聊天类立即失败；状态类保持 pending 并显示“等待 Host”。
- 新机制通过验收**之后**才删 `life-sync.ts` 与对应测试。

M4 同时覆盖 D25 的手机系统工具调用：Host 发出明确动作，Client 校验权限、执行并回执。验收覆盖权限拒绝、重复请求不重复产生副作用、前后台不可用时明确返回状态，并确认 Client 不启动模型调用或自主规划循环。具体工具清单须先确认。

## 7. M5 聊天转发 + 流

**范围**：短时效实时流通道；Host 生成结束后把完整回复落入信箱；断线重连按游标补全并以消息 ID 去重；`chat.cancel`；Host 离线通过 presence 立即失败。

**退出证据**

- 流中途杀掉手机 App，重开后得到完整回复，**模型调用次数为 1**（给出 Host 侧调用日志）。
- 重连与重复拉取不产生重复卡片。
- Host 离线时聊天立即失败并给出明确提示，不排队。

## 8. M6 锁屏通知

**范围**：push gateway（只见推送令牌或句柄、时间、密文大小）；APNs + NSE、FCM、小米；令牌只注册给 gateway（架构文档 §10.3）；通知分类（§10.5）；隐私说明写明元数据边界。

**前置**：M0 的结论；O6 的小米确认；O12 的文案。

**退出证据**

- iOS、带 GMS 的 Android、小米真机：锁屏收到通知，点击后补拉成功。
- gateway 日志与存储不含明文，也不含空间 ID。
- 小米超出每日配额时：推送被拒不影响数据一致性，App 内补拉正常。
- 令牌作废后不能再被推送。
- **长时间锁屏**（例如隔夜）后仍能到达的记录；被杀与 force-stop 的结果如实记录。

## 9. M7 清理与文档

**范围**：删除 Dart 与 TS 的 `space-authority`、转移 UI、`life_host.dart` 转移逻辑；删除 `life-sync.ts` 及对应测试（在 M4 验收之后）；改写 README 与 docs；保留 `device/authority.dart`。

**退出证据**

- 全仓搜索无残留引用，类型检查通过。
- `runtime/test/documentation-contract.test.ts` 与 README 同步更新通过；环境变量文档由 `runtime/src/config/environment-contract.ts` 重新生成。
- 备份分支已建（入口文档 §7）。
- 公开历史与最终树审计：不含内部端点、组织域名、部署文件、未审批素材（`AGENTS.md`）。

## 10. 验收矩阵

起点文档 §8 的场景，在新模型下的对应关系；**这些是预期，当前均没有任何运行证据**。

| 场景 | 期望证据 |
|---|---|
| Client 模式，Host 在线，共享任务到期 | 仅 Host 创建执行记录与模型调用；手机不执行 proactivity，只接收 |
| 独立模式手机的本地定时 | 行为与现状一致，不受影响 |
| Host 运行中短暂断网 | 手机不抢跑；恢复后结果补传，不重复外部动作 |
| 手机离线期间 Host 完成多次任务 | 重连按游标补齐；重复拉取不重复展示 |
| relay 不可达 | 界面明确显示延迟；双方不同时执行共享任务 |
| 发布成功但 ACK 丢失 | 重试得到同一逻辑结果，手机无重复卡片 |
| 手机后台 / 锁屏 | 真实系统通知；点击后补拉证明交付 |
| 撤销设备后重放 | relay 与 Host 都拒绝 |
| Client 版本落后 | 未知类型降级为通用文本卡 |
| 流式中途杀 App | 完整回复补全，模型只调用一次 |
| 双 Client 编辑 | 明确冲突，不静默覆盖 |
| 小米超配额 | 提醒丢失但数据一致，App 内补拉 |
| 模式切换 | 新建 Space，旧数据不迁移 |

每次验收记录：各端构建 SHA、Space / 消息 / 意图 ID、模型调用归属、设备型号与系统版本。

## 12. 风险清单

1. NSE 解密与 APNs 配置（S1）是最大未验证假设。
2. 取代 `life-sync.ts` 改动最大，涉及待办等数据的过渡与冲突语义。
3. 无云账号的托管 relay 只能靠准入、限速与全局上限防滥用（O5）。
4. Android 无 FCM 设备首期不保证锁屏到达；小米归类与透传可靠性未知（O6）。
5. E2E 与通知文字存在冲突：iOS 靠 NSE，Android 靠 data 消息，小米靠通用文案；三者都要真机证据。
6. Client 版本滞后是常态，契约一旦发错类型就无法回收。
7. 本文所有 Android 与小米到达率判断**没有真机证据**。
8. 小米私信模板接入的 2026-12-31 期限：我们走公信，**当前不受影响**；若以后改走私信，需重新评估并注意其对“AI 发起的聊天”与“模糊标题”的排除。
