# Space / Host / Client 第一批实施计划

**目标**：落实 M1 的投递内核，为后续配对、Host、Client 提供可测试基础。本批不等于完成 M1，更不等于完成 M0–M7。

**依据**：同目录 handoff、architecture、migration-map、milestones。用户本轮已授权开始实现和子代理分工、全新上下文评审；此前“只做文档”的状态已被本轮实施请求更新。

**架构**：同仓库独立 `relay/` TypeScript 包，Node 内置 SQLite，无 runtime、Life、模型依赖。网络认证、扫码与密钥管理未实现，必须通过强制注入的可信 `RelayAuthority` 适配器使用投递内核，不能直接将请求字段作为身份。不会开放未经认证的网络服务，也不会自行定义 E2E 密码协议。

**本轮工程选择（不是既定产品决策）**：内核只接受具体接收设备，Host 后续负责 fan-out；采用显式有界存储与队列；历史清理后明确返回游标过期，供后续 snapshot.request 使用。配额为可配置工程默认值，不是托管商业配额。Space 创建、UI、密码学方案保持后续里程碑范围。

## 约束

- 保留旧 Hub/Life/Flutter 实现；本批无删除，无兼容层、无主从迁移。
- relay 仅存不透明密文与投递元数据；业务 kind 不入存储 schema。
- 每次操作复核设备 epoch/撤销；幂等重试不能绕过认证。
- 用户授权本次云环境构建输出与缓存使用 `/workspace` 下隔离目录，替代当前不存在的外置盘。不得清理共享 runtime/dist。
- 不运行真实模型、不发送推送、不部署、不推送 Git。

## 任务与接口

1. **协议边界**：`relay/src/protocol.ts`。`RelayPrincipal`、`RelayEnvelope`、`RelayAuthority`，大小/身份/期限/编码校验。发送必须通过 assertCanSend，读/ACK/presence 必须通过 assertActive。用 Node test 验证错位身份、过大载荷、非法期限。
2. **持久信箱**：`relay/src/mailbox.ts` 与 `relay/test/mailbox.test.ts`。SQLite 事务内分配每设备序号；重复消息返回相同结果，变造内容拒绝；收件、持久 ACK、显式清理与过期游标、全局和设备限额。先运行失败测试，再实现，再验证。
3. **实时投递**：`relay/src/live.ts` 与 `relay/test/live.test.ts`。每设备一个出站连接，心跳过期后立即不可用；流不落盘、不离线排队；受限队列背压关闭，重连后由信箱补齐最终消息。用可控时间和慢消费者测试，不依赖真机。
4. **整合与证据**：独立包工作区/锁文件接线，包说明，V1–V5 核实记录。类型检查、定向测试、受影响现有测试及 diff 检查。全新上下文 agent 一轮独立审查，修复实际问题并重跑相关测试。

## 评审重点

- 发布成功但 ACK 丢失；重启后同 ID 不重新分配序号。
- 双 Client 与跨 Space 隔离；一个设备 ACK 不推进另一个设备。
- 撤销后旧连接、旧 epoch、重复发送均拒绝。
- 慢消费者/失联 Host；内存有界且聊天流不离线排队。
- 清理、容量耗尽、过期消息不伪装成功；客户端能区分需要快照与暂时不可用。
