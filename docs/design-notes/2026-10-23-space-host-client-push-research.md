## 1. 小米推送（Mi Push）

### 1.1 架构（页面确认，pId=1533）

- 云端与客户端保持长连接；在 MIUI / HyperOS 上由系统维护，支持通知栏消息送达。
- 发送方式：服务端 API（Java SDK 与 HTTP）或运营平台；客户端 SDK 面向 Android。
- 目标：Topic、RegID、alias、useraccount。
- 通知栏消息走系统通道，**App 无需常驻后台**；设备在线才送达；离线缓存公信最长 1 天、私信最长 10 天。
- 官方称 MIUI 连接在线时有效推送的送达率在 90% 以上。
- RegID 在重装、清数据、`unregisterPush`、MIUI 卸载上报成功、30 天未连接推送服务器后失效。
- 接入需要在小米开放平台注册开发者、创建应用、开启推送。
- 点击通知后 SDK 把消息数据交给 App。
- 页面**没有**提到：透传消息、包名与签名校验、海外与国内服务器差异、payload 是否对小米服务器可读（只说传输使用高标准加密）。

### 1.2 分类与配额（页面确认，pId=1656）

| 类型 | 说明 | 配额 |
|---|---|---|
| 私信 | 聊天、日程管理、行程提醒、任务进程、设备状态、健康提醒、订单、物流、支付、安全等 | 不限量 |
| 公信 | 内容、营销、平台类；“AI互动”“内容推荐”在其中 | 总量 = 通知已开启设备数 × 倍数（默认 2 倍，有新闻资质 3 倍，设备数下限 1 万）；每设备每应用每天：无资质 5 条，有资质 8 条 |
| 默认 | 未接入任何类别的应用 | 仅可发公信场景；每设备每应用每天 1 条 |

- 配额按“送达量”计算。
- 错误码：`200001` 日配额超限，`200002` QPS 超限。
- 动态关闭率月均超过 0.05% 且 30 天内未整改，公信倍数下调。
- 历史通知：HyperOS 中公信超过 24 小时未点击会消失，私信超过 48 小时（摘要，来自搜索结果）。

### 1.3 2026 年新规（页面确认 + 报道）

- 2026-08-01 零时生效：消息类型由 16 类增至 75 类；私信限 41 个具体场景；每个应用可申请的通道上限由 8 个提高到 30 个。
- 私信必须通过模板接入，并同时携带 `channel_id` 与模板 ID。**2026-12-31 前未完成私信模板接入会影响私信下发。**
- 新增“订阅消息”：用户手动订阅后才能推，仅 8 个类目，权限同私信。
- 旧“个人订阅”通道 2026-08-01 起停止新申请，2026-12-31 起关停。

### 1.4 私信场景规范与对我们的影响（页面确认，pId=2321）

- “好友聊天”**排除“AI发起的聊天”**；示例违规写法：“来自@AI小美的未读消息”。
- “好友聊天”“群组聊天”“群聊互动”**排除主副标题均为模糊内容**；示例违规：“你好 / 你收到一条新消息”。
- 好友聊天要求内容包含**发送人与实际聊天内容**。
- “AI互动”（AI 对话、生成、趣味测试等拉活互动通知）归**公信**。
- “日程管理”要求应用内明确提示用户“设置日程提醒后将收到推送”。

**由此推出（作者推断）**：在 E2E 约束下，我们没法在通知文字里带发送人与实际内容；AI 主动发起的内容本来就更接近公信。所以小米上选择**走公信、使用通用文案、接受每设备每天 5 条**（D20）。聊天回复若强行走私信，有被判违规的风险。若以后想改走私信，需要重新评估并在小米侧确认归类，**不要依赖本次摘要**。

## 2. FCM / Android

### 2.1 页面确认（firebase.google.com/docs/cloud-messaging/android/receive-messages）

- 后台状态下收到**纯 data 消息**会触发 `onMessageReceived`；带 notification 载荷的消息由系统托盘展示，data 在点击后经 launcher Activity 的 extras 交付。
- `onMessageReceived` 的执行窗口很短（OS 延迟、App 启动时间、主线程阻塞都会占用）；超过几秒的工作应交给 `WorkManager`，否则后台执行限制可能暂停或杀掉工作，造成通知延迟或丢失。
- 待发消息超过 100 条或设备超过一个月未连接时，会触发 `onDeletedMessages()`，应用应做一次完整同步（**这与我们的“按游标补拉”设计一致**）。
- 对 AndroidConfigV2，面向用户的通知应使用 `RemoteNotification`，后台数据走 `onBackgroundSyncReceived`；上面的前后台路由表只适用于旧 v1 消息。

### 2.2 页面未覆盖（⚠️ M0 必测）

- 被杀进程与 **force-stop**：一般知识是被用户 force-stop 的应用收不到 FCM，直到用户再次手动打开；本次未查证。
- **Doze**、省电模式、厂商后台限制。
- **Android 12+ 后台启动限制**。
- 消息优先级如何影响送达（页面指向另一页 “Message processing for high and normal priority messages”，本次没有读）。
- 国内无 GMS 设备：FCM 不可用（一般知识）。

### 2.3 设计含义

- 用**纯 data** 消息 + 本地通知，才能做到“先解密再展示”。
- 解密与展示要在很短窗口内完成；失败时降级为通用本地通知，不抛异常。
- 因为 FCM 不保证送达，**数据一致性不能依赖推送**：推送只是唤醒，真正可靠性来自持久信箱与游标补拉。

## 3. iOS / APNs（⚠️ 本次没有读 Apple 文档）

以下全部是一般知识，必须在 M0 对照 Apple 官方文档核实：

- 通知需要 `mutable-content` 才会触发 Notification Service Extension；NSE 有很短的执行时间，超时会展示原始通知。
- NSE 是独立进程，要访问内容密钥需要 App Group 或共享的 Keychain Access Group。
- 标准推送载荷上限约 4 KB。
- 静默推送（`content-available`）会被系统限流，在锁屏与低电量下不可靠，**设计不依赖它**。
- APNs 凭证（密钥或证书）绑定 App 的发布团队，自托管 relay 的用户拿不到，所以 iOS 锁屏必须经我们的 gateway（D18）。
- 用户需要授权通知权限；被拒时只能靠打开 App 补拉。

## 4. 对设计的结论

1. 三个平台的“E2E + 可读通知”靠三种不同机制：iOS 用 NSE，Android 用 data 消息，小米用通用文案；**其中只有小米是确定的**，另外两个都等 M0。
2. 推送只是唤醒，不是可靠通道。可靠性来自持久信箱、游标补拉、按 ID 去重（架构文档 §6）。
3. gateway 是平台约束下的必需品；隐私说明必须公开写明它可见的元数据。
4. 小米的配额意味着：高频主动建议不能每条都推，要合并或只发“有新内容”（架构文档 §10.5）。
