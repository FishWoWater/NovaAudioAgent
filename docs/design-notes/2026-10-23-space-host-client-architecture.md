# Space / Host / Client 目标架构

日期：2026-10-23  
基线：`v1.0.0dev`，`ecb533f9`  
状态：设计。✅ 表示产品已确认，💡 表示建议待评审，❓ 开放，⚠️ 未验证。决策编号（D*）与开放问题编号（O*、V*）见[入口文档](2026-10-23-space-host-client-handoff.md)。

## 1. 总览

```text
 ┌──────────────── Space（本地空间：一套密钥 + 数据）────────────────┐
 │                                                                  │
 │   Host（桌面端，唯一）                  Client（手机，可多个）     │
 │   ┌──────────────────────┐             ┌────────────────────┐    │
 │   │ runtime / context    │             │ 无 runtime         │    │
 │   │ 权威 Life 数据       │             │ 展示缓存 + 意图队列│    │
 │   │ 后台任务 / proactive │             │ 原生渲染           │    │
 │   │ (原 Hub 并入)        │             │ 原生能力(待定 O2)  │    │
 │   └─────────┬────────────┘             └─────────┬──────────┘    │
 └─────────────┼──────────────────────────────────────┼──────────────┘
               │ 出站连接                             │ 出站连接
               ▼                                      ▼
         ┌───────────────────────────────────────────────┐
         │ relay（盲中转，可自托管，开源）               │
         │ 密文信箱 · 实时流 · 在线状态 · 唤醒           │
         └──────────────────────┬────────────────────────┘
                                │ 内容无关的唤醒请求
                                ▼
                    push gateway（我们托管）
                    APNs · FCM · 小米 Mi Push
```

三条硬约束：

1. runtime 与 context 只在 Host（或独立模式的手机）上，relay 与 gateway 永远不执行模型。
2. relay 与 gateway 看不到内容（E2E，D16）；能看到的元数据要在隐私说明里写明。
3. 一个 Space 只有一个 Host，状态只由 Host 写；Client 提交的是**请求**。

## 2. 角色与模式

| 模式 | 创建时选择 | 能力 | 限制 |
|---|---|---|---|
| 独立运行 | ✅ D2 | 当前移动端完整版：本地聊天、feed、完成待办、本地定时 | 锁屏等状态下后台定时任务无法可靠运行；无 relay、无同步 |
| Client | ✅ D2 | 展示 Host 状态、回传意图、转发聊天、锁屏通知 | 没有本地聊天与 runtime（D11）；Host 离线时聊天不可用 |
| Host | 桌面端 | 持有 runtime、context、权威数据、后台任务 | 一个 Space 一个；损坏即丢失（D8） |

模式切换 = 新建 Space（D7）。一次安装可以有多个相互独立的 Space（D2，本地数据隔离细节见 O9）。

## 3. 信任模型与密钥

✅ 原则：E2E，配对时交换密钥，relay 只见密文与游标；撤销设备时轮换空间密钥（D16）。

💡 建议的结构（**需密码学评审，见 O7；不要自造协议**）：

- 每个设备一对身份密钥；Host 生成并持有 Space 的根身份。**空间 ID** 是 Space 公钥的摘要，对 relay 不透明。
- 消息体用 Space 内共享的对称内容密钥加密（AEAD）；消息头由发送设备签名，relay 验签后才接收。优先使用成熟库提供的原语（例如 libsodium 的密封盒与 AEAD，或 Noise 框架），避免手写拼装。
- 撤销设备：Host 生成新内容密钥并只分发给仍有效的设备；旧设备拿不到之后的消息。已经落在旧设备上的历史不能撤回。
- iOS 的 Notification Service Extension 是独立进程，需要通过 App Group / Keychain Access Group 读到内容密钥。这是一个必须在 M0 验证的点。
- relay 能看见的元数据：空间 ID、设备 ID、序号、时间、密文大小、通道类别。**设备 ID 与通道类别是否也应加密**是一个取舍：加密越多，relay 越难实现背压与过期，见 §5。

## 4. 配对与撤销

💡 流程草案（现有 `runtime/src/hub/pairing.ts`、`pairing-http.ts`、`clients/flutter/lib/personal/hub_pairing.dart`、设备 epoch 可能可复用，**未读实现，待核实**）：

1. 用户在 Host 创建 Space，选择 relay（自托管地址或我们托管的地址）。
2. Host 展示二维码：relay 地址、空间 ID、一次性配对密钥、Host 公钥。
3. Client 扫码，用一次性密钥完成密钥交换，向 Host 发送自己的设备公钥与推送凭证句柄（见 §10.3）。
4. Host 在桌面端确认新设备（显示指纹，防止被扫描劫持），再把内容密钥发给它。
5. 撤销：Host 标记设备失效、递增 epoch、轮换内容密钥，并通知 relay 拒绝该设备的后续收发。

验收要求：撤销后重放旧设备的旧消息被拒；二维码一次性且有过期时间。

## 5. relay

### 5.1 职责

| 能力 | 说明 |
|---|---|
| 密文信箱 | 持久、按序、可补拉。承载状态、事件、意图回执 |
| 实时流 | 短时效、不保证补发。承载聊天流式预览 |
| 在线状态 | Host 与 Client 心跳；让 Client 在 Host 离线时**立即**得到失败，而不是等超时 |
| 唤醒 | 有新消息时，触发 push gateway；不含内容 |
| 配额与准入 | 见 §11 |

relay **不**做：搜索、过滤、解密、执行任何任务、解释业务字段。

### 5.2 与现有 Hub 的关系

可复用或搬迁的只有内容无关的部分：`routing.ts` 的 presence / inbox / ack / deadline，`store.ts` 的信封存取与配对邀请。其余 relay 代码需要新写。现有 Hub 的 Life、context、schedule 逻辑**不进 relay**，并入 Host。详见迁移图。

### 5.3 连接方式

✅ 产品连接方式统一为 relay，取代原先依赖 Tailscale 的连接流程（D24）。relay 底层可以评估复用 Tailscale；这是实现候选，尚未确认可行性或选型，不要求用户理解或配置两套连接方式。局域网直连是否保留另议。

💡 当前传输提案是每设备主动连出一条 WebSocket，HTTPS 兜底。若评估基于 Tailscale 实现，需核实部署与自托管方式、账号与设备准入、移动端集成及后台限制、运维与许可成本。无论选何种底层，都要单独满足密文信箱、游标补拉、配对撤销与系统推送的需求；不能把底层联网能力当成这些应用协议已经实现的证据。

### 5.4 Client 的手机系统工具（O2，待确认）

“原生任务”原先混用了两种含义，后续分别称为：

- **手机系统工具调用**：Host 给出明确动作与参数，例如创建一条系统提醒、读取获授权的日历、请求用户拍照。Client 校验权限、必要时请求用户确认，执行动作并返回结果；不自行调用模型或规划下一步。
- **手机自主 Agent 任务**：Host 只交付目标，手机自行观察、调用模型、规划与执行多步操作，例如自主操作某个 App 完成目标。这需要本地 Agent 执行循环，不能直接视为“无 runtime Client”的普通工具。

💡 建议 Client 保留第一类，第二类暂不纳入。Host 决定下一步，Client 只提供获授权的工具；具体工具清单、权限和确认规则仍需产品确认。系统提醒事项也不等于手机运行 Nova 的定时 Agent：前者可由手机系统在指定时间提醒，后者需要 Agent 执行任务。

相机、日历、提醒等能力在桌面端也可能存在，此处关注的是手机上的具体数据与设备。工具可用性受平台权限、锁屏和前后台限制；Client 应返回不可用或等待用户操作，不能承诺随时远程调用。现有 `ios_native` / `android_native`、`device_run_task` 是待拆分核查的实现入口，不是可以原样保留的结论。

## 6. 信封与投递语义

### 6.1 信封（💡 提案）

```text
Envelope {
  v:      信封版本
  space:  不透明空间 ID
  id:     发送方生成的消息 ID（去重键）
  from:   发送设备 ID
  to:     接收设备 ID 或 "host" / "clients"
  chan:   mailbox | stream            // relay 只需要区分这两类行为
  seq:    由 relay 在 (space, 接收方) 内分配的单调序号（仅 mailbox）
  ts:     发送时间
  ttl:    过期时间（stream 与 chat 意图必须有）
  sig:    发送设备对头部与密文的签名
  body:   密文（内含业务 kind、版本、内容）
}
```

业务类别（state / event / intent / receipt / chat / wake）放在密文里，relay 不需要知道。relay 只需要 `chan` 与 `ttl` 就能完成存储、过期和背压。

### 6.2 投递规则

- **至少一次 + 去重**：发送方用稳定 `id` 重试；接收方按 `id` 去重落盘；展示层再按业务 ID 与版本去重。起点文档 §5 指出：通知成功、结果已落盘、用户已读是不同状态，不要混为一谈。
- **游标**：每个接收设备有自己的已确认游标，重连时从游标补拉。
- **ACK 丢失**：发布成功但 ACK 丢失，重试得到同一逻辑结果，手机不出现重复卡片。
- **过期**：stream 与聊天意图的 ttl 短（参照现有命令 15 分钟上限，`routing.ts` deadline 校验）；状态信箱的保留期与容量上限 ❓ 待定（nanoMuse 的参考数字：每账号 2 万条、单条 16 KB、墓碑 30 天，仅供参考）。
- **背压**：每连接出站队列设上限，超限断开并要求重连补拉。

### 6.3 信箱过期后的重建（O11）

E2E 下 relay 看不到实体键，没法按实体做压缩。两个方案：

- **A（💡 倾向）**：Client 游标过期或冷启动时，发一个 `snapshot.request` 意图，Host 回一份完整快照。Host 是唯一权威，逻辑简单；代价是 Host 离线时 Client 只能显示旧缓存。
- **B**：给每条状态消息附一个由密钥派生的不透明实体标签，relay 按标签只保留最新一条。代价是泄露“同一实体被更新了几次”的元数据。

## 7. 展示契约

### 7.1 方向

Host 推**版本化的结构化数据**，Client 原生渲染；不做服务端驱动 UI（离线可用、速度快、符合“Client 不持有可分叉状态”）。

### 7.2 内容

| 类型 | 现状（⚠️ 静态阅读） | 要补的 |
|---|---|---|
| goal / todo / idea | `runtime/src/hub/life-projection.ts:9-14` 已有，字段为 `id,title,note,status,importance`，todo 另有 `due,goal_id`，idea 有 `goal_id`，goal 有 `success_criteria` | 带出实体 `version`（reducer 内部已有，`life-projection.ts` 的 `applyLifeSyncProjection` 里 `version:(old?.version??0)+1`） |
| profile | 只有 `about`（最长 5000 字） | 版本字段已有（`profile.version`），投影要带出 |
| Timeline | **没有** | 条目类型、忽略状态，必须新增 |
| feed 卡片 / 通知 | 在 Host 的 NotificationService 与 Feed 里，不在同步契约内 | 新增 |
| 聊天消息 | 不在同步契约内 | 新增 |

投影边界原则沿用现有注释：不导出原始证据、来源授权、消息、连接器凭证、推断出的 profile 分区（`life-projection.ts` 顶部注释）。**不要为了报告同步而扩大成全量状态复制**（起点文档 §3）。

### 7.3 版本规则（✅ D14）

1. 只增不改；废弃字段保留。
2. 未知字段忽略。
3. 未知卡片类型降级成通用文本卡（标题 + 正文）。
4. 配对握手交换协议版本；Host 记录每个 Client 支持的最低版本，不向它发送无法降级的类型。
5. 应用商店审核造成 Client 版本落后是**常态**，不是异常。

字段清单与最低版本协商是 M3 的首要产出（O4）。

## 8. Client 意图

### 8.1 意图类型

| 方向 | 内容 |
|---|---|
| Client → Host | 完成待办、忽略卡片、创建/编辑目标与待办、编辑 profile about、手机采集输入、聊天消息、取消聊天、快照请求 |
| Host → Client | 意图回执、状态更新、事件、聊天流与最终回复 |

### 8.2 必须保留的语义

用“意图 + Host 落盘 + 回投影”取代 `runtime/src/hub/life-sync.ts` 的双写 outbox 时，**不能只写“带幂等 ID”**。codex 评审指出，并经我对照 `clients/flutter/lib/personal/local_life.dart` 核实，现有实现有以下语义，替代方案必须等价或更好：

1. **持久化 pending**：意图在发出前写盘（`local_life.dart:146` 附近，记录 `op_id`、`input`、`result`、`entity_id`）。提交后断网或退出再启动，沿用原 `op_id`，不丢、不重复创建。
2. **ID 重映射与依赖顺序**：本地创建的实体先有临时 ID，Host 落盘后返回正式 ID；后续 pending 里引用旧 ID 的 `id`、`goal_id`、`idea_id` 要改写（`:249` 附近）。先建目标、再建关联待办，必须保证顺序。
3. **冲突反馈**：两端改同一实体（例如 profile about）需要版本冲突，不能静默覆盖；冲突时保留未提交修改并接受 Host 快照（`:266` 附近，`LifeSyncConflict`）。

保留这些语义**不要求保留双主**：Client 只发请求，Host 是唯一写入方，冲突由 Host 以 `base_version` 判定。

### 8.3 回执与过期

- 每个意图在 Host 侧有按 `op_id` 的幂等回执表。
- 聊天意图短时效；Host 离线时通过 presence 立即失败（D11）。
- “完成待办”等状态类意图 💡 建议**不自动过期**，保留在 Client 的 pending 里直到有回执或用户撤销；Host 长期不在线时界面要显示“等待 Host”。现有 Flutter outbox 条目在 15 分钟过期（`clients/flutter/lib/agent/hub_tasks.dart:160-170`，子代理报告，未复核），这对状态类意图不合适。

## 9. 聊天转发与流式（D11–D13）

```text
Client                    relay                    Host
  │  chat.send(ttl 短)     │                        │
  │───────────────────────>│───────────────────────>│  presence 离线 → 立即失败
  │                        │                        │  runtime 生成
  │   stream 帧(预览)      │<───────────────────────│  chan=stream，不补发
  │<───────────────────────│                        │
  │                        │   final(turn_id)       │  落入信箱 chan=mailbox
  │<───────────────────────│<───────────────────────│
  │ 以 turn_id 去重，替换预览                       │
```

- 流只是预览。断线、切后台、锁屏都不影响 Host 完成生成；重连后按游标取到完整回复。
- 去重键是 turn / message ID，不重复展示，**不重复调用模型**。
- 取消：`chat.cancel` 意图。
- relay 需要同时支持持久信箱与短时效流两类通道。

## 10. 锁屏通知与 push gateway（D17–D20）

### 10.1 为什么要有 gateway

APNs 与小米推送的凭证绑定 App 发布者，自托管 relay 的用户拿不到。所以即使 relay 完全自托管，iOS 与小米的锁屏通知也必须经我们托管的 gateway（D18）。这是平台约束，不是设计选择，隐私说明必须公开写明。

### 10.2 gateway 可见 / 不可见

- 可见：设备推送令牌（或我们给的句柄）、时间、密文大小、平台、优先级。
- 不可见：消息内容、空间 ID（💡 建议不传给 gateway）。

### 10.3 令牌与滥用（💡 需评审）

直接把设备令牌交给 relay 会让自托管 relay 的运营者拿到令牌，也让任何人都能向 gateway 发推送。建议：

1. Client 把推送令牌**只注册给 gateway**，gateway 返回一个不透明的 `push_handle` 与一个只对该 handle 有效的推送凭证；
2. Client 经配对后的加密通道把 handle 与凭证交给 Host / relay；
3. relay 在有新信箱消息时，凭 handle 与凭证请求 gateway 唤醒；
4. gateway 按 handle 限速并允许 Client 随时作废。

### 10.4 各平台

| 平台 | 方案 | 状态 |
|---|---|---|
| iOS | 可见提醒通知，`mutable-content`，密文放在自定义字段；Notification Service Extension 在端上解密后改写标题与正文；解密失败或超长降级为通用文案。**不依赖静默推送**（iOS 会限流，锁屏下不可靠）。载荷上限约 4 KB，实施前查 Apple 官方文档 | ⚠️ 未验证；本次没有读 Apple 文档 |
| Android（FCM） | 纯 data 消息交给 App，`onMessageReceived` 解密后发本地通知（官方页面确认：后台状态下 data 消息会触发 `onMessageReceived`） | ⚠️ 机制已由官方页面确认；被杀 / force-stop、Doze、Android 12+ 后台限制该页面**没覆盖**，需 M0 真机 |
| 小米 | 通知栏消息由系统直接展示，App 无法先解密；使用**公信通用文案**，接受每设备每应用每天 5 条（D20）；超配额靠 App 内补拉 | ⚠️ 官方页面摘要；透传消息能否可靠唤醒被杀进程页面未提（O6） |

通用文案不是“你好 / 你收到一条新消息”这种两者皆模糊的写法能进私信；因此在小米上我们**不走私信**，而是明确走公信并接受配额。详见推送调研文档。

### 10.5 通知分类

💡 从产品语义出发先分类，再映射到各平台通道：

| 类别 | 例子 | 期望 |
|---|---|---|
| 对话回复 | 聊天最终回复 | 尽量到达，通用文案 |
| 用户设定的提醒 | 日程、待办到期 | 尽量到达 |
| AI 主动建议 | proactive feed、日报 | 可降级，受配额；可只发“有新内容” |

### 10.6 与现有通知系统的关系（O10）

`docs/proactive-notification-channels.md` 描述了 `runtime/src/notifications` 的持久 outbox、主渠道绑定与适配器接口（`NotificationChannelAdapter.inspect / prepare / send`）。💡 建议把“手机推送”做成一个新适配器：沿用其“生产者意图 → outbox → 路由”结构、去重键（业务事件 + 内容版本 + 提醒次数）、`unknown`（可能已送达，不自动重发）等语义。这是我读文档后的**推断，没有读适配器代码**，需要核实后再决定。

## 11. 托管 relay 的滥用与配额（O5）

没有云账号，就没有身份可用来限流或计费。已知问题（codex 评审，推断）：空间 ID = 公钥时，攻击者可以批量生成公钥绕过**按空间**配额；签名只证明持钥。

至少需要：

- **创建准入**：新空间要通过某种门槛（候选：邀请码、工作量证明、App Attest / Play Integrity 之类的设备证明、按来源 IP 的创建限速）。❓ 选哪种待定。
- **入口限速**：连接数、消息速率。
- **全局上限**：存储总量、流量。
- **push 配额**：按 `push_handle` 与全局两层。
- 自托管 relay 可不设上限，由运营者自己决定。

## 12. Host 侧的后台工作

Host 在 Client 模式下是**唯一**后台执行者：proactive 生成、定时任务、共享任务都在 Host 上跑，结果落盘后经 relay 推给 Client。对起点文档的四个决定：

| 起点文档 | 新模型 |
|---|---|
| A 以什么决定执行端 | 由 Space 模式固定，Host 持续有效；不按在线状态动态切换 ✅ |
| B 哪些任务交给 PC | Client 模式下，自动生成与定时都由 Host 执行；依赖手机原生能力的任务见 O2 ❓ |
| C Host 不可用时 | 等待，不自动在手机重跑；界面显示等待 Host；错过的时间槽如何补见 O3 ❓ |
| D “推给手机”承诺 | 前台约 5 秒内、重连补齐去重、**锁屏通知首期必须**（D17）；已读 / 撤回 / 更新是否跨端一致首期至少保证不丢不重 |

注意：独立模式的手机仍按现有逻辑自己跑本地定时；这条不改。

## 13. 失败模式

| 场景 | 预期行为 |
|---|---|
| Host 休眠 / 断网 | Client 展示最后缓存，标明“Host 不在线”；聊天立即失败；状态类意图保留在 pending；推送不会产生 |
| Host 恢复 | 游标续传；处理积压意图；按 `op_id` 幂等，不重复变更 |
| relay 不可达 | Host 与 Client 都不发新消息，本地继续；恢复后补拉 |
| ACK 丢失 | 重试同一 `id`，对端去重，不出现重复卡片 |
| Client 版本落后 | 未知类型降级成通用文本卡；Host 不发送无法降级的类型 |
| 设备被撤销后重放 | relay 与 Host 都拒绝 |
| 流中途 Client 被杀 | 重启后按游标得到完整回复，不重复调用模型 |
| 推送超配额 / 平台不支持 | 不影响数据一致性，只影响提醒；用户打开 App 时补拉 |
| Host 损坏 | Space 丢失（D8），产品上明说 |

## 14. 不做的事

不做平权、多 Host、手机接管后台任务、Host 备份恢复、在线自动选主、模式切换迁移、Client 本地聊天（D2、D5、D7–D9、D11）。如果实施中发现必须突破其中任何一条，请先回到产品负责人，不要自行加机制。
