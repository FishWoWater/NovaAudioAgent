# Nova 瘦身计划（v0.2.0dev）

> 状态：**仅计划，未执行任何精简。** 分支 `plan/slim-2026-09-13`，基线 v0.2.0dev `62520e20`。审计依据：2026-09-13 六路只读审计（realtime、executors、memory/graph、host/transport、desktop、runtime tests）+ Codex 目录冗余专项核查。前置方案：feature/ponytail-simplify 分支 `docs/design-notes/2026-09-12-whole-repo-reduction-plan.md`。

## Context

实测（git 跟踪文件，不含 thirdparty/node_modules）：生产侧 115,378 行（含 desktop scripts 11k、native 4k、webui、ios），测试侧 121,261 行。竞品 qwen-audio-agent 约 50k / 40k。六路只读审计的共同结论：**几乎没有死代码**，臃肿来自四种习惯：

1. 每个内部接缝都当成对抗性信任边界，各自手写防御（native C 文件锁/inode 校验、进程 env 快照、store 自校验、Codex schema 手工重推导）。
2. 同一概念多层重复实现（"等人类决策" 4 套；desktop 传输 4–5 层；4 个子系统各自一套 worker/client RPC）。
3. 迁移期/发布期的验证工具长期留存（Python 对齐审计 JSON 5k 行、oracle 测试已在挂、发布验签/attestation/包检查脚本 6.3k 行 + 其测试 5.2k 行）。
4. 测试无共享 harness（realtime-service.test.ts 11k 行、273 个用例、5 套手工构造器）。

**已定的产品边界（2026-09-13 与产品负责人确认）**：语音双管线保留；Vision Guard/camera 全部保留；iOS 配对保留；WebUI 备份到独立本地分支后删除；图谱退役（但迁出新记忆底座需要的 `sensitivity.ts` 与可复用存储基础，并同步改 03/06 spec）；Windows 原生防护层简化为 OS 原语；service.ts 必须拆。

**诚实的算术**：在上述约束下，可删的生产代码约 **29k 行（≈25%）**，加上把评测脚手架搬出 src 约 2k（≈2%），JSON 账本 5.8k 不在分母内。**达不到 40%**。剩余 13% 只能来自语音管线合并（已排除）或 Orb/设置 UI 简化（约 2%，视觉会变）。本计划按 ~27% 交付，不虚报。

工作前提：`git status` 显示 v0.2.0dev 工作区有几十个未提交修改，**先提交或 stash**；先建备份分支 `backup/v0.2.0dev-2026-09-13`。runtime 测试当前 2,583 过 / 22 挂（挂的集中在 volcengine oracle，本计划会删它）。

3. **host-delivery**：先在原文件把 queue/ack/urgent/proof 的写入口收敛为 enqueue/bind/settle/requeue/retire，再整体迁出（map 随方法一起走，不留在 service）。delivery pass 返回"是否需重驱 continuation"，由 service 在锁释放后调用。
4. **tool-continuations**：ack 预约走 host-delivery 窄入口；user origin ledger 留在 service 只保留一份。
5. **project-confirmation-flow**：保持 `handleEvent` 中确认隔离在 `session.accept` 之前；commit await 期间若 expiry 已拿事实归属则不重复发布。

7. 硬约束：锁顺序 reconnect → delivery，delivery 与 continuation 锁不同持；新 owner 不 import `RealtimeService`；每个 await 两侧保留 token/epoch/commit 失效检查；不新增依赖；public API（`flushHostItems`、`driveContinuations`、`playback*`、`deliveryState`）保持兼容。
