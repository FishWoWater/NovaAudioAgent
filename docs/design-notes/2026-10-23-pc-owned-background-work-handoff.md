# PC 执行后台任务、手机接收结果：设计讨论 Handoff

日期：2026-10-23  
检查基线：`v1.0.0dev`，`ecb533f9`  
状态：设计讨论材料，未实施。现状来自静态源码检查，未做三端实机验收。

## 1. 用户目标

> phone / PC / Hub 都在线时，phone 不执行 proactivity 或类似的定时任务，由 PC 执行；PC 生成的结果同步推给手机。

希望避免手机和 PC 重复生成、重复耗费模型资源、产生不一致的结果，同时让手机及时看到 PC 的产出。

已经明确的是“三端在线”场景；PC 离线后的接管策略、手机后台通知要求及任务覆盖范围尚未决定，不能当作已确认需求。

## 2. 当前结论

**现有版本有主设备身份、任务 owner 和跨端数据同步基础，但没有完成上述端到端行为。**

| 能力 | 已实现事实 | 与目标的差距 |
|---|---|---|
| 主设备身份 | 持久化 `mobile_primary` / `pc_primary`；在线状态不触发选主 | “PC 在线”本身不会使手机统一停跑 |
| 手机 Profile 自动生成 | 自动生成检查 `authority.canPublish` | 只证明该入口受控，不能推断所有 proactivity / 定时任务都受控 |
| 手机本地定时任务 | 本机 owner 的启用任务会被领取；前台每 30 秒检查，另有原生唤醒接入 | 未依据 PC 在线或 `pc_primary` 统一让出执行权 |
| Hub 共享定时任务 | owner、revision、slot 去重、checkpoint、显式 handoff 已存在 | 不是按在线状态自动接管；当前注册和交接目标限制为 desktop |
| Life 同步 | 同步目标、想法、待办，以及 Profile 的 `about` 字段 | 不包含完整生成画像、主动消息、完整聊天或全部定时报告 |
| Context 同步 | 支持授权事实、修正、带证据引用的派生条目 | 是专门的数据契约，不是通用结果收件箱 |
| 手机接收 | 前台立即同步，成功后约每 30 秒轮询；离开前台停止该同步定时器 | 不能等同于实时推送或系统后台通知 |

此前概括的“Profile 可同步”应按上述字段范围理解，不应据此承诺完整生成画像已跨端共享。

## 4. 首先需要讨论的四个决定

### A. 以什么决定执行端？

建议首期采用“明确选择 PC 为后台执行设备，身份持续有效”。PC 在线时执行；短暂断线不让手机抢跑。这与现有 authority / owner 机制较接近。

如果产品要求“任何 PC 一上线就自动接管，离线后手机自动接管”，这是另一档范围：必须明确在线判定、心跳过期、网络分区、旧执行者恢复后的 fencing，以及多个 PC 的选择。不能只在手机加一个 `if (pcOnline) return`。

需确认：用户接受持久化 PC 模式，还是必须按在线状态动态切换？若选后者，接管等待时间和允许接管的任务类别是什么？

### B. 哪些任务交给 PC？

建议先列清单，再统一执行判断。

| 类别 | 建议讨论起点 |
|---|---|
| 主动建议、摘要、Profile / Timeline 等自动生成 | 候选 PC 统一执行范围；逐项确认实际入口 |
| 用户创建的通用定时 Agent 任务 | 可纳入共享 owner；已有手机任务需显式迁移 |
| 依赖手机原生能力的任务 | 保留手机执行或显式委托，不能因 PC 在线全部禁用 |
| 用户正在进行的聊天和手动操作 | 不因后台计算归属而自动禁用 |
| 数据同步、结果接收、必要的手机采集 | 继续运行；它们是结果到达和输入可用的前提 |

这些是范围建议，不是已经确认的例外。需要特别区分“停止自动生成”和“关闭手机全部定时器”。

### C. PC 或 Hub 不可用时怎么办？

建议首期共享任务等待恢复，不自动在手机重跑；UI 显示等待执行设备。只有纯本地手机任务继续按原有归属运行。

待决定：错过的时间槽是跳过、只补最近一次，还是逐次补跑？正在运行时断网，是否允许完成本地计算并延后发布？涉及外部动作、状态不明的任务如何人工恢复？

### D. “推给手机”具体承诺什么？

需要分别确认：

1. 手机在前台且连通：希望结果在多少秒内出现？建议讨论目标为 5 秒内。
2. 手机离线后重连：补齐结果，重连或重复通知不重复展示。
3. 手机在后台 / 锁屏：是否要求系统通知？若要求，需要单独设计 iOS / Android 的投递和安装配置，不能由前台长连接替代。
4. 已读、撤回、更新是否跨端一致？首期至少保证结果不丢失且不重复展示；提醒策略需单独确定。

## 5. 建议的最小完整链路（待评审）

```text
任务定义及执行归属 → PC 领取本次运行 → PC 生成并持久化结果
                                         ↓
                               Hub 持久化可同步结果
                                         ↓
                              通知手机存在新的结果
                                         ↓
                        手机按游标拉取、去重落盘、展示
```

Hub 负责协调与存储，不在首期新增模型执行职责。通知只是唤醒拉取的信号；可靠性来自持久化结果和断线补拉。

设计前先检查现有 Hub task events、PC 通知服务和定时结果数据能否复用。只有无法表达的部分才扩展，避免重新建一套通用任务系统。

结果协议至少要能表达：稳定结果 ID、生产设备、所属任务与运行、结果版本、生成时间、内容或可访问引用、同步游标。具体字段名、正文大小和附件取回方式待协议评审；不要直接同步整个 runtime 状态或本机文件路径。

执行与结果交付分别去重：任务以稳定 schedule / slot / run 标识防止重复领取；手机以结果 ID 和版本防止重复展示。通知成功、结果已落盘、用户已读是不同状态。

## 6. 交接与存量任务

现有 Hub 共享任务只允许 desktop 注册 / 作为交接目标。不能将其描述为已经支持手机本地任务迁往 PC。

迁移前需核对手机任务的模型配置、工具权限、输入数据和 PC 可执行性；模型凭据不应随任务定义直接复制。

建议迁移流程：冻结旧端的新领取 → 处理完或明确终止在途运行 → 保存已执行时间槽和游标 → PC 确认接收 → 提交归属变更。失败时保留旧记录和明确状态，不能先删手机任务再尝试在 PC 创建。

尤其需要确认：用户在手机创建一个任务时，默认创建“共享 PC 任务”还是“手机本地任务”？已有任务是否需要用户逐项选择迁移？这会直接影响 UI 和兼容策略。

## 7. 实施前应完成的盘点

- 列出 PC 与手机所有自主触发入口及其实际调用链，覆盖前台、原生后台唤醒和恢复运行；目前只读检查尚未覆盖所有 proactivity 路径。
- 对每个入口标注输入来源、执行设备要求、现有 owner、产出类型、结果落盘位置和通知出口。
- 检查 PC 获得手机相关上下文的授权与新鲜度；“PC 在线”不能代表已经具备运行输入。
- 检查已有 task events / notification / schedule result 契约是否满足手机展示与补拉，再确定最小扩展。
- 列出需联动的调用方、持久化 schema、迁移、UI、测试和 fixtures；此次尚未形成可直接开工的完整改动清单。

## 8. 建议验收场景

| 场景 | 期望证据 |
|---|---|
| 三端在线，同一共享任务到期 | 仅 PC 创建执行记录和模型调用；手机仅接收结果 |
| 手机前台定时器和原生唤醒同时触发 | 不绕过归属检查，不出现重复 run |
| PC 运行途中短暂断网 | 手机不抢跑；恢复后结果可补传，不重复外部动作 |
| 手机离线期间 PC 完成多次任务 | 重连按协议补齐，重复拉取不重复展示 |
| Hub 不可达 | 明确显示延迟状态，双方不同时认领共享任务 |
| PC 模式下手机仍有本地专属任务 | 按已确认范围执行，不能误停必要手机功能 |
| 归属交接发生在运行中 | 交接被等待或阻止；旧 owner 不能继续领取新任务 |
| 结果发布成功但 ACK 丢失 | 重试得到同一逻辑结果，手机不出现重复卡片 |
| 手机后台 / 锁屏 | 若纳入范围，以实际系统通知和点击后补拉证明交付 |
| 已有手机任务迁移 | 保留执行游标与历史，无重复补跑、数据丢失或凭据泄露 |

验收应记录各端构建 SHA、任务 / run / 结果 ID，以及模型调用归属；仅凭 UI 显示“在线”无法证明没有双端执行。

## 9. 本次讨论希望产出的决定

- 执行策略：持久化 PC 模式，还是在线自动选主。
- 首期范围：具体纳入哪些自动生成和定时任务，哪些保留手机执行。

- 交付承诺：前台延迟目标，后台系统通知是否首期必须。

## 10. 边界与未验证项

本次仅新增 handoff 文档，没有修改运行逻辑、调用真实模型、运行构建测试、变更部署或发布代码。源码结论限定于 `ecb533f9`；实际安装包和运行配置可能不同。

最大风险是将“主设备发布权限”“任务执行 owner”“设备在线状态”当成同一个概念：只修改其中一处，无法保证没有重复执行，也无法保证结果能够到达手机。
